# S1 driver: working notes

Chronological log of the work on the S1 mini printer (label "Type S1", Bluetooth name `PPS1_4367`). Raw material for the article.

## Ground rules (set by the author)

The Luck Jingle licence and service agreement (clause 8.2.1) forbids, unless the law allows it or the vendor agrees in writing, among other things: decompiling or disassembling the app, copying or altering client-server data, and using third-party tools to log in to or use its software and services. So this work:

- talks only to the printer, never to the Luck Jingle app or its servers;
- does not decompile the app or capture its traffic, and creates no account;
- reuses no vendor assets such as logos, icons or fonts;
- copies no code from S1Print, minixprint or other projects;
- never sends firmware updates or setting changes to the printer.

## Provenance: this run is not blind

Before this work started, the same session had read public protocol notes from S1Print and minixprint, so it knew the command set and the likely 384-dot head. It cannot count as a blind replication. Commands learned from those notes are marked as such below, and are accepted only once confirmed on this printer.

## Discovery

1. **USB:** the printer enumerates as vendor `PPS1`, product `LJPrt ComPort`, ID `3021:6001`, with a CDC serial port and a printer-class interface (7/1/2).
2. **BLE:** it appears as `PPS1_4367_BLE`. Service `FF00`: notify `FF01`, write `FF02` (with and without response), notify `FF03`. It advertises no service UUID, so Web Bluetooth must filter by name prefix. macOS reports MTU 240.
3. **Identity queries** (`10 FF 20 F0`, `10 FF 20 F1`, `10 FF 20 F2`, `10 FF 50 F1`, `10 FF 40`, `10 FF 11`, `10 FF 13`, `10 FF 70`; from third-party notes): no reply over USB, with or without explicit DTR and RTS. No reply over BLE either, in any subscribe order or write mode, and no notifications at all, not even flow-control credits. The USB cable was connected during all of these.
4. **Test 1, standard raster over USB** (`GS v 0`, 48 bytes wide, 88 rows, then `ESC J 80`; no vendor command): see below.
5. **The link answered once the USB cable was unplugged.** The same BLE queries then got replies at once. This is one observation, and the cause is not established. Model `S1_LYiN48D_GY`, firmware `V1.9.11`, battery `00 64` (100%), status `00`, auto power-off `1E` (30 minutes). This model string settles the identity: the unit tested here is the same model as the S1 tested by S1Print, on different firmware (V3.0.3 there).
6. **Flow control:** on connect `FF03` sends `01 05` and `02 C8 00`, then `01 01` after every write. This is the same credit scheme as the XL-P801X (`01 nn` = credits, `02 lo hi` = packet size, here 200 bytes). Unlike the XL-P801X, credits keep coming while `FF01` is subscribed.
7. **Tests 2 and 3, BLE with credits (photo `IMG_2743`):** both printed. Standard `GS v 0` alone works, with no vendor command. The half-width bars stop at the centre, which confirms 48 bytes = 384 dots. The stripes of test 1 are not on this strip, so there is no evidence that USB printed. Sent 3,659 and 5,003 bytes; the printer replied `OK` once, and it is not clear to which job.
8. **Anomaly:** the 60-dot feed after test 2 does not show, and the first bar of test 3 overlaps the half bar of test 2 by about 26 rows, measured from the photo. Hypothesis: something retracts the paper at the start of a job. Test 4 checks this.
9. **Test 4, feed and job framing (photo `IMG_2744`):** all five groups printed whole and separate, with clean gaps, including the groups sent with standard commands only. The overlap from note 8 did not come back, so its cause is unknown. The printer replied `OK` once per group, shortly after each raster, and the vendor end command brought no reply of its own. Decision for the first web driver: use standard `GS v 0` and `ESC J` only, wait for `OK`, and add vendor commands only if a test shows they are needed.

10. **Test 5, long page (photo `IMG_2745`):** an 80 mm page sent as 255-row blocks (A) and as one raster command (B). Both printed with unbroken vertical lines, so no blank band showed at the block boundaries in this single test, at about 4 kB/s from macOS. Each job got one `OK`, about 0.4 s after the last write, so `OK` is not per raster block. Decision: send blocks, because a cancel can then end cleanly at a block boundary.
11. **First web driver (`luck-jingle-s1/web/index.html`):** derived from the XL-P801X page. Standard `GS v 0` and `ESC J` only, strict credits with no fake credit on a stall, and one read-only battery query on connect (`10 FF 50 F1`). It sends no reset, density or other setting command. It has not printed yet from Chrome. Tested so far without the printer: its protocol code against a simulated printer (blocks, cancel, packet shrink, stall, missing `OK`, disconnect), and page rendering in headless Chrome. While a PDF was loaded and rendered there, the page's only requests were itself and pdf.js from cdnjs, plus local `data:` and `blob:` URLs. Worker requests were not captured. The page's content security policy sets `connect-src 'none'`. The dots per mm are still an assumption: the calibration page has to confirm them on paper.
12. **First print from Chrome (photo `IMG_2746`):** the web driver printed the calibration page over Web Bluetooth from a browser, with no app and no account. The first and last ticks of the ruler both print, so nothing is clipped across the 384 dots. Measured on the photo: about 2.52 pixels per dot across and 2.48 to 2.53 per row down, so the dots look square to within about 2%. No ruler was in the shot, so the 8 dots per mm is still not measured directly. The six non-white grey steps match the preview. The blank margins look unequal, about 2.6 mm on the left and 4.7 mm on the right, which may be a real offset of about 1 mm or an effect of the curled paper. Blank paper above the first printed row and below the last suggest the head sits about 8 mm from the tear edge, less than the 15 mm first guessed from test 4, so the default feed after a job drops to 10 mm.
13. **White gaps at block boundaries (photo `IMG_2749 2`):** a dark screenshot, 1,128 rows, printed from Chrome in five bands with a white gap between them. The band lengths match the block sizes (255, 255, 255, 255, 108 rows, last band about 0.43 of the one before it). The gaps look about 6 mm long and the text continues across them, so no rows seem lost. The driver sends no feed between blocks (checked against the simulated printer, which cannot show what the real one does), so the paper movement comes from the printer. This contradicts the decision in note 10, which rested on one test with a light page. That test also joined the blocks into one stream, so a boundary fell inside a BLE packet, while the web driver starts a new packet for each block. So the web driver did not send what test 5 had tested. Test 6 (`tools/test_blocks_ble.py`) separates the two differences.
14. **Calibration page printed again:** the page had been opened with `?calibration`, which added the page on every reload, so it printed with the user's image. That URL option is removed.
15. **Web driver changed before test 6 was read:** it now sends one raster command per page, because a page then has no internal boundary, whatever the cause turns out to be. The cost is on cancel: the printer expects every row it was promised, so the rest of the page goes out as white rows and uses paper. The page also got a simpler layout, 2 mm of blank space around text, and no longer adds pages from the URL.
16. **Test 6, what the log shows (paper result still to come):** with each block in its own packets (A dark, C light) the printer replied `OK` twice, once after each block. With the blocks joined (B) or one command (D) it replied `OK` once. So in A and C the printer treated the end of the first block as the end of a job. All four sent at about 4.2 kB/s, so a dark page did not visibly slow the data.
17. **Gap inside a single raster command (photo `IMG_2751`):** the demo receipt, 474 rows in one command from Chrome, shows the same white gap of about 5 to 6 mm, cutting the "Sandwich" line at about row 271. So the block boundaries of note 13 are not the whole explanation. Test 5's single command, 640 rows from Python, showed no gap, including at rows 256 and 512, so the row count alone does not explain it either. Open question: does the Chrome stream stall, and does a stall in the data make the printer move the paper?
18. **Test 6, paper result (photo `IMG_2753`):** A (dark, blocks in separate packets) and C (light, blocks in separate packets) both have the white gap at the block boundary. B (dark, blocks joined in one stream) and D (dark, one command) have none. So darkness is not the cause, and the block boundary gap appears when one raster ends and the next one starts in a new packet. All four came from Python, so this does not yet explain the gap inside the single command printed from Chrome (note 17).
19. **Test 7 and timing runs, log only (paper result still to come):** the strip holds, in order: `1 pauses`, `2 stopped`, `2 after link closed`, `3 stopped`, `3 after pause`, `4 after idle`, `CHROME RUN`, `PYTHON RUN`. A new job got `OK` both after the link closed and after a 3 s pause with the link open, though only 160 of the 300 promised rows had been sent. The last two runs print the same receipt from a test Chrome and from Python, each after 15 s idle. Chrome: 22,763 bytes in 5.24 s, longest wait between writes 90 ms (before row 266). Python: 22,763 bytes in 5.19 s, longest wait 103 ms (before row 375). So this Chrome run shows no large stall in the data, and the stall idea from note 17 has no support so far from the timings.
20. **Correction to note 17:** the receipt in `IMG_2751` came from the older page, not from the single raster command. It has 24 dashes in the rule (the newer demo has 23) and no 2 mm text padding, and row 255, the block boundary, falls 17 rows into the "Sandwich" line in that layout, which is where the cut is. So the gap there was the block boundary again, and nothing so far shows a gap inside a single raster command.
21. **Test 7, paper result (photo `IMG_2755`):** pauses of 0.2, 0.5 and 1.0 s inside one raster leave no gap, and the rows carry on correctly (`1 pauses`). A raster left unfinished ends when the link closes (`2 after link closed` prints correctly, after a gap) and also after 3 s with the link open (`3 after pause` prints correctly, with no gap). A raster after 20 s of idle link has no gap (`4 after idle`). So a printer stop needs no disconnect: stop sending, wait, and a new command is safe. The wait must be more than 1 s, and 3 s is tested. `CHROME RUN` and `PYTHON RUN` are not in this photo.
22. **Real stop:** Stop now ends sending at once, on a whole row, waits 3.5 s for the printer to drop the raster, then feeds 10 mm. Run through the page on the real printer (log only, paper result still to come): stopped at 20% of a 17.4 cm job, finished in 3.6 s, and the next job got `OK`. A first attempt never started the long job because of a timing error in the test script, so the strip has an extra `AFTER STOP` and a handwritten test line before the `STOP TEST` lines.
23. **Gap fix confirmed from Chrome (photo `IMG_2756`):** `CHROME RUN`, the demo receipt in one raster command through Web Bluetooth, has no gap and the "Sandwich" line is whole. `PYTHON RUN`, the same bytes from Python, looks the same. The paper from the stop test (`STOP TEST`, `AFTER STOP`) is not in this photo.
24. **Native Mac driver (`mac/`):** a SwiftUI app with the same controls as the web page, built from the XL-P801X app. Changes from that app: 384 dots, roll paper only, trim of blank edges, no reset or density command, one raster per page, strict credits with no fake credit on a stall, `FF01` subscribed for `OK`, and the stop logic from note 21. HTML input was dropped and RTF is read as RTF only, because HTML import can fetch remote content. The Command Line Tools here do not ship the plugin for SwiftUI's `@State` macro, so view state lives in small observable objects and the app still builds without Xcode.
25. **First prints from Swift, log only (paper result still to come):** `tools/real_print.sh` drives the app's own link and job code on the real printer. Receipt: 10,091 bytes, `OK` after 2.42 s. 30. **Head test, correcting note 28:** in all four blocks the 3-dot wave is dark along the whole width, the 2-dot and 3-dot lines are solid, the 1-dot line is thin but unbroken, and the first and last ticks print. So no weak columns showed, and the pale patch of note 28 did not come back on the same kind of stroke. In this photo the patch is on the large bold `F` of `FAKE LABEL`, and it looks silvery. 31. **Small text in a shrunk A4 page is not reliable for numbers:** the fake A4 report prints with its layout intact and its headings readable, but the table values degrade. In the bitmap sent to the printer, not only on paper, `13.8` is hard to tell from `12 9` and `0.60 to 1.10` reads `0.60 to 1 10`, with the decimal point gone. Thin vertical table lines come out dotted. This is a limit of 384 dots across a page about four times wider than the paper, and the preview shows it before printing. Tuning the threshold can help lines but cannot make digits this small reliable.
32. **How small is too small, measured:** rendering digits through the same steps as the drivers, at 16 sub-dot positions, on Helvetica, Times and Georgia. At 6 dots per em two different digits can come out identical. The fewest dots that differ between any two digits, in the worst font and position: 2 at 10 dots, 3 at 12, 7 at 14, 9 at 16. A decimal point left ink at every position from 11 dots up, and at 7 of 16 positions at 5 dots. Both drivers now warn below 14 dots per em, using the smallest type on the page, or an assumed 10 pt on a page with no text layer. This measures the bitmap only, not the head or the paper. It cannot see text inside a plain image, so images get no warning. The fake A4 page is about 8 dots per em.
33. **Print as text:** both drivers can replace a warned page with its plain text at 11 pt. Each row of the fake table stays on one line, and on both macOS and pdf.js the words keep the page's order. The cost is paper: 24.2 cm for the fake A4 page, against about 3.6 cm for its picture. The layout is gone, and other PDFs may give another text order, so the page says to check it against the original.
34. **Real run through the model the window uses, log only (paper result still to come):** report as text printed in 22 s; note in 2 s; stop at 30% of five copies, ended 3 s later with the queue cleared and notice `Stopped`; next job `OK` in 1 s. 37. **Print as text on paper, 11 pt against 8 pt (photo `IMG_2764`):** with the fake report as text at 11 pt and its table at 8 pt on one strip, every value is correct at both sizes: `5.4`, `3.9 to 5.6`, `13.8`, `12.0 to 16.0`, `0.82`, `0.60 to 1.10`. At 8 pt each row fits on one line, using 342 of the 352 dots available, and the decimal points stand clear of the digits in the bitmap. 9 pt would wrap that row too, at 385 dots. So both drivers now use 8 pt: 22.6 dots per em, and 13.9 cm for the page instead of 24.2 cm. 43. **Printing over the Classic Bluetooth serial port, and link encryption (2026-11-19, on a Linux computer, not the Mac):** the printer has two Bluetooth identities. `PPS1_4367` (Classic, Serial Port profile) was already paired and bonded on this computer; when and how it was paired is not recorded. `PPS1_4367_BLE`, the one the drivers use, was not paired. `tools/test_print_spp.py` opened RFCOMM channel 1 with encryption required on the socket, and the kernel listed that link as `AUTH ENCRYPT`. The battery query answered `00 4d`. One `GS v 0` raster of 128 rows and one `ESC J` (6155 bytes) were sent, with no reply within 4 s, and the user reported that the strip printed and reads `SPP 19-11-2026`. Limits: the flags are what the computer's kernel reports, not a capture from the air; the pairing probably needed no confirmation on the printer, so it would not stop someone in the middle at pairing time (not checked); nothing was tried on the Mac, from the web page, or with a long page.
44. **Printer choice, print-dialog files and the paired serial link in the drivers (2026-11-21, code only, nothing printed):** three changes, prompted by the defects listed in note 42 and by note 43. First, the Mac apps of both printers no longer connect by themselves to the first device with a matching name. With no printer chosen they list what they find and wait; the user presses Connect, and the choice is saved and used alone on later launches, with Change printer to choose again. The identifier saved by older versions is discarded, so the choice is made once more after the update. Second, in the S1 Mac app files from the print dialog or the Dock icon now open with their preview and wait for Print by default. With the option to print them at once turned on, a document with a small-text warning still waits. The XL-P801X app had the same path, for dropped files too, and now also waits by default; it has no small-text warning. Third, the S1 drivers can print over the paired serial link of note 43, and prefer it. The Mac app lists `/dev/cu.*` devices whose name contains `PPS1`, opens the chosen one in raw mode with POSIX calls, writes 512-byte chunks off the main thread with at most two waiting, and uses the same job and Stop code as over BLE. It counts the printer as present only when the battery query is answered, and ends a job after the last write, the port's output queue emptying (if macOS reports it) and 3 s, as sent but unconfirmed unless an `OK` arrives. A stop over this link waits 1.5 s longer than over BLE, because a write ends when the system has the bytes. The web page has the same over Web Serial: it asks for the Serial Port service (`0x1101`) or, with Choose another serial port, any port, since on a Mac the paired printer is a plain serial port. Both show which link is in use, encrypted or not. Tested: `node tools/tests/send.test.mjs` (21 checks) and the new `node tools/tests/serial.test.mjs` (22 checks: bytes in order, chunk size, waiting for the port, stop on a whole row then a wait, abort before the start, a stalled port, a lost link, connecting with and without a battery answer) all pass, and the page loads in headless Chromium on Linux with the new buttons. Not tested: the Swift code was not compiled, because this computer has no macOS SDK, so neither app change has been built, including the XL-P801X one; `mac/test.sh` was not run; nothing was printed over the serial link from the Mac or from a browser; no long page and no Stop over that link; whether macOS reports the port's output queue; whether a Mac encrypts the link as Linux did.
